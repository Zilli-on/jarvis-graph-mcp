# 002 — `mcp` 2.0.0 removed `mcp.server.fastmcp`; fresh installs broke

## Task

Bring up `jarvis-graph-mcp` from a clean `pip install -e .` in an
isolated venv, per the documented install path in README.md.

## What failed

```
File "src/jarvis_graph_mcp/server.py", line 29, in <module>
    from mcp.server.fastmcp import FastMCP
ModuleNotFoundError: No module named 'mcp.server.fastmcp'
```

Zero tools register. The server cannot start at all.

## Root cause

`pyproject.toml` declared `"mcp>=1.0.0"` with no upper bound.
`mcp` 2.0.0 restructured `mcp.server` and dropped the `fastmcp`
submodule (confirmed by enumerating `mcp.server`'s submodules on
2.0.0: no `fastmcp` anywhere, and no standalone `fastmcp`
distribution is pulled in as a transitive dependency either).
`server.py:29` is the only affected import site.

## Fix

Pin below the breaking major: `"mcp>=1.0.0,<2"`.

Verified in a clean venv with `mcp==1.29.0`: 18 tools register via
`asyncio.run(mcp.list_tools())`, and a live `summary` call against
a real repo (jarvis-graph-lite itself) returns correct structured
data — 64 files, 723 symbols, 2975 calls, 0 parse errors.

## Prevention rule

Same failure class as 001 (declared install contract didn't match
reality), with one addition: **cap the major version of every
runtime dependency.** `>=X` with no upper bound means any future
upstream major release can break the install contract between two
of our own commits, with no PR of ours to catch it.

Also: this repo's install-path CI job runs `on: pull_request` only.
An unpinned dependency can go quietly broken between pushes with
nothing to catch it. Recommend adding a scheduled (`cron`) run of
the same install-path job so an ecosystem break like this surfaces
within a day, not whenever someone next happens to push.
